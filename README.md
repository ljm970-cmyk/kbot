# kbot

키움증권 REST API 기반 무한매수법(TQQQ / SOXL) 자동매매 봇.
텔레그램으로 조작하고, 장 마감 후 자동 정산한다.

---

## 무엇을 하는가

매 거래일 프리장 시작에 맞춰 그날의 주문을 계산해 예약으로 걸고,
마감 후 체결을 정산해 T값·평단·잔금을 갱신한 뒤 다음날 계획을 세운다.

```
프리장 시작        3/4 목표 지정가매도 접수
프리장 +15분       LOC/MOC 예약 접수 (별지점·평단·폭락대비·쿼터매도)
프리장 +35분       예약주문 검증 (거부된 건 확인)
마감 +30분         EOD 정산 → T값 갱신 → 모드 전환 판정 → 다음날 계획
```

시각은 서머타임과 조기폐장에 따라 매일 다시 계산된다. 주말·미국 휴장일은 건너뛴다.

| | 서머타임 | 비서머타임 |
|---|---|---|
| 프리장 시작 | 17:00 KST | 18:00 KST |
| 장 마감 | 05:00 KST | 06:00 KST |
| 조기폐장일 마감 | 02:00 KST | 03:00 KST |

## 설치

파이썬 3.11 이상이 필요하다.

```bash
git clone https://github.com/ljm970-cmyk/kbot.git ~/kbot
cd ~/kbot
./deploy/setup.sh
```

`.env`를 채운다.

```bash
cp .env.example .env
chmod 600 .env
vi .env
```

| 변수 | 설명 |
|---|---|
| `KIWOOM_APP_KEY` / `KIWOOM_APP_SECRET` | 키움 REST API 키 (필수) |
| `TELEGRAM_BOT_TOKEN` | BotFather 발급 토큰 (필수) |
| `TELEGRAM_ADMIN_ID` | 관리자 숫자 ID. **비우면 기동을 거부한다** |
| `KIWOOM_MOCK` | `true`면 모의투자 서버 |
| `KBOT_DRY_RUN` | `true`면 주문을 전송하지 않는다 |

## 실운영 전 점검

API 클라이언트는 문서만 보고 작성했다. 실제 응답과 맞는지 순서대로 확인한다.

### 1. 배관 확인

```bash
venv/bin/python main.py --check
```

TQQQ·SOXL 시세와 USD 예수금이 나오면 통과다.

### 2. SOXL 거래소구분 확정

시세가 0으로 나오면 `stex_tp`가 틀린 것이다. TQQQ는 NASDAQ(`ND`)로 확정이지만
**SOXL은 NYSE Arca 상장이라 키움이 `NY`로 잡는지 `NA`로 잡는지 문서만으로는 알 수 없다.**

```bash
venv/bin/python -c "
import asyncio
from config.settings import ConfigLoader
from kiwoom.api_client import KiwoomAPIClient
async def m():
    async with KiwoomAPIClient(ConfigLoader.load().kiwoom) as api:
        print('SOXL', await api.resolve_exchange('SOXL'))
asyncio.run(m())"
```

결과를 `kiwoom/constants.py`의 `EXCHANGE_MAP`에 고정한다.

### 3. 모의투자로 주문 왕복

```bash
venv/bin/python main.py --mock --check
```

LOC(30)·MOC(33) 주문이 실제로 접수되는지, `ust21205` 조회에 뜨는지 확인한다.
모의투자가 미국주식 LOC/MOC를 지원하지 않으면 실계좌 최소 수량으로 같은 순서를 밟는다.

### 4. 주문 미전송으로 관찰

```bash
venv/bin/python main.py --dry-run
```

며칠간 텔레그램으로 오는 주문 계획을 눈으로 확인한다.
별지점·수량·폭락대비 가격이 손으로 계산한 값과 맞는지 본다.

### 5. 실운영

```bash
./deploy/setup.sh --service
sudo systemctl enable --now kbot
sudo journalctl -u kbot -f
```

첫 사이클은 1주짜리 최소 금액으로 돌려보는 편이 안전하다.

## 핵심 개념

### T값은 하루 단위로 계산한다

"별지점과 평단이 둘 다 체결되면 +1, 하나만 되면 +0.5"는 개별 체결만 봐서는
판정할 수 없다. 그래서 그날 체결된 태그 집합을 모아 한 번에 계산한다.

```python
c = TCalculator(40, t=8.0)
c.apply_normal_day(DayFills.from_list(
    [FillKind.QUARTER_SELL, FillKind.STAR_BUY, FillKind.AVG_BUY],
    holdings_after=60))
# 8.0 × 0.75 + 1 = 7.0   (방법론 9: 매도 먼저, 매수 나중)
```

| 상황 | T |
|---|---|
| 1회 매수 (별지점 + 평단 모두) | +1 |
| 절반 매수 (둘 중 하나) | +0.5 |
| 폭락대비 매수 | 변화 없음 |
| 쿼터 LOC 매도 | × 0.75 |
| 3/4 지정가매도 단독 | × 0.25 |
| 지정가매도 + LOC매수 | × 0.25 + 1 (또는 + 0.5) |
| 지정가매도 + 쿼터매도 | 0 (사이클 종료) |
| 리버스 매도 | × 0.90 (20분할) / × 0.95 (40분할) |
| 리버스 쿼터매수 | + (분할수 − T) × 0.25 |

### 주문 태그가 T값의 전제다

키움 API에는 사용자 주문 태그 필드가 없다. 체결 통보는 `ord_no`만 돌려주고,
예약주문은 그 `ord_no`조차 알려주지 않는다(`ust21205` 응답에 없음).

그래서 주문을 낼 때 태그와 주문 속성을 `core/order_registry.py`에 적어두고,
체결이 들어오면 **주문단가**로 역조회한다. 무한매수법은 하루 주문의 단가가
모두 다르기 때문에(별지점 / 평단 / 폭락대비 5단계) 단가만으로 갈린다.

이 불변조건이 깨지면 T값 계산이 무너지므로 계획 단계에서 단가 충돌을 검사한다.

> **주의**: LOC는 주문단가와 체결단가가 다르다. 76.02에 걸어도 종가 68.10에
> 체결된다. 체결단가로 매칭하면 엉뚱한 주문에 붙는다.

### 별지점은 모드마다 정의가 다르다

| | 별지점 |
|---|---|
| 일반모드 | 평단 × (1 + 별%) |
| 리버스모드 | **직전 5거래일 종가의 평균** |

평단 대비 −15%/−20%는 리버스 **종료조건**이지 별지점이 아니다.

별%는 T가 분할수의 절반일 때 정확히 0이 되고, 그 이후 음수가 된다(후반전).

### 소진 판정 (2026-08-02 보강 반영)

| 모드 | 소진 기준 | 이후 동작 |
|---|---|---|
| 일반 | 1회 매수로 1주도 살 수 없음 | 리버스모드 전환 |
| 리버스 | 쿼터매수(잔금÷4)로 1주도 살 수 없음 | 매수 중단, MOC 매도만 |

리버스모드에서는 T가 19나 39를 넘어도 쿼터매수가 가능한 동안 계속 진행한다.
소진은 매일 재판정되므로, 매도대금으로 잔금이 차오르면 다시 쿼터매수로 돌아간다.

## 텔레그램

관리자만 조작할 수 있다. `TELEGRAM_ADMIN_ID`에 쉼표로 여러 명을 넣을 수 있다.

스케줄러·EOD 결과는 자동으로 관리자에게 전송된다. 특히 아래는 반드시 확인한다.

- **예약주문 거부** — 증거금 부족, 가격제한폭 초과 등
- **체결 매칭 실패** — 원장에 없는 체결(수동 주문 등)
- **이상 조합** — 종가 판정상 불가능한 체결 조합이 관측됨

## 알려진 미확인 사항

실행으로 검증되지 않은 부분이다. 운영 전에 확인할 것.

1. **SOXL의 `stex_tp`** — `NA`로 두었으나 추측이다. `resolve_exchange()`로 확정할 것
2. **예약주문 접수 응답 구조** — `rsrv_ord_no` 필드명이 실제와 맞는지
3. **시세 부호 처리** — `"-198.4500"`을 하락 표시로 보고 절댓값을 취한다
4. **모의투자의 LOC/MOC 지원 여부**
5. **SEC/TAF 요율** — `config/fees.py`의 기본값은 대략치다. 증권사 고지 기준으로 갱신할 것
6. **리버스 소진 후 MOC 매도 수량** — 1단계와 동일하게 10/20등분(내림)으로 두었다.
   40분할 기준 보유 19주 이하가 되면 20등분이 0주가 되어 매도가 멈춘다.
   잔여 물량 처리 규칙이 방법론에 없어 경고만 남기고 사람이 판단하도록 했다

### 방법론 문서의 오타로 보이는 곳

리버스 쿼터매수 예제(3-(3))에서 1회 매수금액 544.47, 별지점 48.61일 때
폭락대비가 `45.37 / 41.88 / 38.83 / 36.29`로 적혀 있는데 세 번째가 맞지 않는다.

```
544.47/12 = 45.3725 → 45.37  일치
544.47/13 = 41.8823 → 41.88  일치
544.47/14 = 38.8907 → 38.89  문서는 38.83
544.47/15 = 36.2980 → 36.29  일치
```

네 번째가 `/15`와 정확히 맞으므로 세 번째도 `/14`가 맞다고 보고 계산값을 쓴다.

## 안전장치

- `KBOT_DRY_RUN=true` — 주문 계획만 세우고 전송하지 않는다
- `--check` — 시세·예수금만 확인하고 종료
- 매수 주문에 MOC/STOP을 넣으면 전송 전에 거부된다 (키움이 지원하지 않음)
- 방법론 8번 — 현재가에서 크게 벌어진 LOC는 현재가 +15% **단건**으로 대체
- 예약주문 접수 후 `ust21205`로 생존 확인
- 상태 파일은 임시파일 → fsync → 교체로 원자적으로 저장
- 일별 정산 결과를 `data/archive/`에 append-only로 남긴다 (상태 손상 시 재구성용)

개인 사용 목적. 투자 손실에 대한 책임은 사용자 본인에게 있다.
자동매매는 예기치 못한 주문을 낼 수 있으므로, 운영 중에도 증권사 앱으로
실제 잔고와 주문을 주기적으로 대조할 것.
