# kbot

키움증권 REST API 기반 무한매수법(TQQQ / SOXL) 자동매매 봇.
텔레그램으로 조작하고, 장 마감 후 자동 정산한다.

---

## 무엇을 하는가

매 거래일 프리장 시작에 맞춰 그날의 주문을 계산해 예약으로 걸고,
마감 후 체결을 정산해 T값·평단·잔금을 갱신한 뒤 다음날 계획을 세운다.

```
프리장 시작        3/4 목표 지정가매도 접수
프리장 +15분       LOC/MOC 예약 접수 (별지점·평단·폭락대비·쿼터매도)
프리장 +35분       예약주문 검증 (거부된 건 확인)
마감 +30분         EOD 정산 → T값 갱신 → 모드 전환 판정 → 다음날 계획
                   → 증권사 잔고 대조 → 텔레그램 리포트 전송
```

시각은 서머타임과 조기폐장에 따라 매일 다시 계산된다. 주말·미국 휴장일은 건너뛴다.

| | 서머타임 | 비서머타임 |
|---|---|---|
| 프리장 시작 | 17:00 KST | 18:00 KST |
| 장 마감 | 05:00 KST | 06:00 KST |
| 조기폐장일 마감 | 02:00 KST | 03:00 KST |

## 설치

파이썬 3.10 이상이 필요하다.

```bash
git clone https://github.com/ljm970-cmyk/kbot.git ~/kbot
cd ~/kbot
./deploy/setup.sh
```

`.env`를 채운다.

```bash
cp .env.example .env
chmod 600 .env
vi .env
```

| 변수 | 설명 |
|---|---|
| `KIWOOM_APP_KEY` / `KIWOOM_APP_SECRET` | 키움 REST API 키 (필수) |
| `TELEGRAM_BOT_TOKEN` | BotFather 발급 토큰 (필수) |
| `TELEGRAM_ADMIN_ID` | 관리자 숫자 ID. **비우면 기동을 거부한다** |

| `KBOT_DRY_RUN` | `true`면 주문을 전송하지 않는다 |

## 실운영 전 점검

API 클라이언트는 문서만 보고 작성했다. 실제 응답과 맞는지 순서대로 확인한다.

### 1. 배관 확인

```bash
venv/bin/python main.py --check
```

TQQQ·SOXL 시세와 USD 예수금이 나오면 통과다.

### 2. SOXL 거래소구분 확정

시세가 0으로 나오면 `stex_tp`가 틀린 것이다. TQQQ는 NASDAQ(`ND`)로 확정이지만
**SOXL은 NYSE Arca 상장이라 키움이 `NY`로 잡는지 `NA`로 잡는지 문서만으로는 알 수 없다.**

```bash
venv/bin/python -c "
import asyncio
from config.settings import ConfigLoader
from kiwoom.api_client import KiwoomAPIClient
async def m():
    async with KiwoomAPIClient(ConfigLoader.load().kiwoom) as api:
        print('SOXL', await api.resolve_exchange('SOXL'))
asyncio.run(m())"
```

결과를 `kiwoom/constants.py`의 `EXCHANGE_MAP`에 고정한다.

### 3. 모의투자로 주문 왕복

```bash
venv/bin/python main.py --mock --check
```

LOC(30)·MOC(33) 주문이 실제로 접수되는지, `ust21205` 조회에 뜨는지 확인한다.
모의투자가 미국주식 LOC/MOC를 지원하지 않으면 실계좌 최소 수량으로 같은 순서를 밟는다.

### 4. 주문 미전송으로 관찰

```bash
venv/bin/python main.py --dry-run
```

며칠간 텔레그램으로 오는 주문 계획을 눈으로 확인한다.
별지점·수량·폭락대비 가격이 손으로 계산한 값과 맞는지 본다.

### 5. 실운영

```bash
./deploy/setup.sh --service
sudo systemctl enable --now kbot
sudo journalctl -u kbot -f
```

첫 사이클은 1주짜리 최소 금액으로 돌려보는 편이 안전하다.

## 핵심 개념

### T값은 하루 단위로 계산한다

"별지점과 평단이 둘 다 체결되면 +1, 하나만 되면 +0.5"는 개별 체결만 봐서는
판정할 수 없다. 그래서 그날 체결된 태그 집합을 모아 한 번에 계산한다.

```python
c = TCalculator(40, t=8.0)
c.apply_normal_day(DayFills.from_list(
    [FillKind.QUARTER_SELL, FillKind.STAR_BUY, FillKind.AVG_BUY],
    holdings_after=60))
# 8.0 × 0.75 + 1 = 7.0   (방법론 9: 매도 먼저, 매수 나중)
```

| 상황 | T |
|---|---|
| 1회 매수 (별지점 + 평단 모두) | +1 |
| 절반 매수 (둘 중 하나) | +0.5 |
| 폭락대비 매수 | 변화 없음 |
| 쿼터 LOC 매도 | × 0.75 |
| 3/4 지정가매도 단독 | × 0.25 |
| 지정가매도 + LOC매수 | × 0.25 + 1 (또는 + 0.5) |
| 지정가매도 + 쿼터매도 | 0 (사이클 종료) |
| 리버스 매도 | × 0.90 (20분할) / × 0.95 (40분할) |
| 리버스 쿼터매수 | + (분할수 − T) × 0.25 |

### 주문 태그가 T값의 전제다

키움 API에는 사용자 주문 태그 필드가 없다. 체결 통보는 `ord_no`만 돌려주고,
예약주문은 그 `ord_no`조차 알려주지 않는다(`ust21205` 응답에 없음).

그래서 주문을 낼 때 태그와 주문 속성을 `core/order_registry.py`에 적어두고,
체결이 들어오면 **주문단가**로 역조회한다. 무한매수법은 하루 주문의 단가가
모두 다르기 때문에(별지점 / 평단 / 폭락대비 5단계) 단가만으로 갈린다.

이 불변조건이 깨지면 T값 계산이 무너지므로 계획 단계에서 단가 충돌을 검사한다.

> **주의**: LOC는 주문단가와 체결단가가 다르다. 76.02에 걸어도 종가 68.10에
> 체결된다. 체결단가로 매칭하면 엉뚱한 주문에 붙는다.

### 별지점은 모드마다 정의가 다르다

| | 별지점 |
|---|---|
| 일반모드 | 평단 × (1 + 별%) |
| 리버스모드 | **직전 5거래일 종가의 평균** |

평단 대비 −15%/−20%는 리버스 **종료조건**이지 별지점이 아니다.

별%는 T가 분할수의 절반일 때 정확히 0이 되고, 그 이후 음수가 된다(후반전).

### 소진 판정 (2026-08-02 보강 반영)

| 모드 | 소진 기준 | 이후 동작 |
|---|---|---|
| 일반 | 1회 매수로 1주도 살 수 없음 | 리버스모드 전환 |
| 리버스 | 쿼터매수(잔금÷4)로 1주도 살 수 없음 | 매수 중단, MOC 매도만 |

리버스모드에서는 T가 19나 39를 넘어도 쿼터매수가 가능한 동안 계속 진행한다.
소진은 매일 재판정되므로, 매도대금으로 잔금이 차오르면 다시 쿼터매수로 돌아간다.

## 텔레그램

**단일 계좌 모델이다.** 키움 앱키가 하나이므로 사용자를 나누는 것은 의미가 없다.
여러 사람이 봇에 접근해도 결국 같은 계좌를 건드린다. 기존 텔레그램 코드는
`get_state(user_id, ticker)` 처럼 사용자별 상태를 전제했는데, `StateManager` 가
`user_id` 를 받아서 무시하는 호환 메서드를 제공해 호출부를 고치지 않아도 되게 했다.
접근 권한은 `TELEGRAM_ADMIN_ID` 로 통제한다.

관리자만 조작할 수 있다. `TELEGRAM_ADMIN_ID`에 쉼표로 여러 명을 넣을 수 있다.
인증은 전역 가드(`group=-1`)로 처리하므로 명령·대화형 마법사·버튼 콜백이 모두 막힌다.

| 명령 | 설명 |
|---|---|
| `/status` `/st` | 관제탑 현황 |
| `/orders` | 주문 내역 — 실시간 미체결 + 예약주문 (🤖 봇 / 👤 직접 구분) |
| `/history` `/hist` | 거래 히스토리 |
| `/start` | 초기 설정 마법사 |
| `/config` | 분할·원금·수수료 변경 |
| `/fix` | 수동 거래 보정 (버튼식, 인자를 주면 텍스트 방식) |
| `/next` | 다음 거래일 일정 |
| `/pause` `/resume` | 주문 접수 정지·재개 |
| `/run <작업>` | 즉시 실행 (plan/submit/verify/eod) |
| `/report [종목]` | 일자별 매매 이력 리포트 |
| `/stats [종목]` | 누적 성과 (사이클·승률·손익) |
| `/health` | 운영 상태 점검 (가동·토큰·체결수신·종목별 현황) |
| `/panic` | 긴급 정지 — 전 종목 정지 + **봇이 낸** 예약주문 취소 |
| `/halt` | 신규 주문만 정지 (접수된 주문은 그대로) |
| `/unhalt <종목>` | 정지 해제 (인자 없이 치면 정지 목록) |
| `/calceod` | 강제 EOD 계산 |
| `/help` | 명령어 안내 |

한글로도 된다: `상태` `주문내역` `히스토리` `설정` `일정` `일시정지` `재개` `통계` `보정` `상태점검` `패닉`

### /panic 과 /halt 의 차이

| | `/halt` | `/panic` |
|---|---|---|
| 신규 주문 | 막음 | 막음 |
| 접수된 예약주문 | 그대로 | **취소** |
| 확인 절차 | 없음 | 버튼으로 한 번 더 |

`/panic`은 **봇이 낸 주문만** 취소한다. 원장(`core/order_registry`)에 기록된
예약번호와 대조하므로, 사용자가 직접 건 주문은 대상에서 빠진다. 결과는 건별로
보여준다 — 급한 상황에서 "몇 건 취소됨"만 알면 나머지를 직접 처리할지 판단할 수 없다.

취소 가능 시간(08:00~22:25 KST)이 아니면 정지만 되고 취소는 실패한다. 그 사실도 함께 알린다.

### 주문 종류별 전송 방식

| 주문 | 방식 | 시각 |
|---|---|---|
| 목표 지정가매도 | 실시간 | 17:01 (프리장 시작 +1분) |
| LOC 매수·쿼터매도 | 실시간 | 17:02 |
| MOC 매도 (리버스 첫날) | 예약 | 17:02 |

지정가와 LOC를 **프리장에 실시간으로** 낸다. 실측(2026-09-22)으로 둘 다 프리장에
바로 접수되어 미체결에 표시됨을 확인했다.

예약주문으로 걸면
- 정규장 개장(22:30) 때에야 실주문으로 넘어가서, 지정가매도가 프리장 구간을 놓친다
- 증거금·가격 거부가 22:30에 결정돼, 입금하거나 다시 낼 시간이 없다
- 날짜 규칙과 취소 가능 시간(08:00~22:25) 제약이 있다

MOC는 프리장 실시간 접수가 아직 확인되지 않아 예약으로 둔다.

17:35와 22:40에 주문을 검증한다. LOC는 종가 전에는 체결될 수 없으니,
미체결에서 사라졌으면 거부·취소로 보고 알린다.

실측(2026-09-22)으로 프리장에 낸 실시간 LOC가 22:40 정규장에서도 미체결로 유지됨을
확인했다. 예약 검증은 처리 에러·무효만 거부로 본다 — "취소"는 거둔 예약이라
거부가 아니다.

### 가격제한폭 대체주문 (방법론 8)

주문가가 현재가보다 **25% 이상** 높으면 증권사가 거부할 수 있다고 보고,
현재가 × 1.15 에 1회매수액 전체를 단건으로 낸다.

기준이 25%인 이유: 별%는 T=0에서 최대 20%(SOXL 40분할)다. 사이클 초반에는
현재가와 평단이 비슷해 별지점이 현재가보다 19~20% 위에 놓이는데, 이건 정상이다.
기준이 18%였을 때 이 정상 구간에서 매일 대체주문이 발동해 별지점·평단 2분할이
단건으로 뭉개졌다(실측 2026-09-23: 평단 151.95 / 현재가 150.86 / T=1).

25%는 정상 구간을 넘어서므로 평단이 현재가보다 한참 위인 진짜 폭락에서만 발동한다.
실제 거부 한계는 아직 모른다 — 실시간 주문이라 거부되면 접수 즉시 알 수 있다.

### 두 종목 동시 운용 (TQQQ + SOXL)

이미 한 종목을 운용 중이어도 `/start` 또는 관제탑의 **종목 추가** 버튼으로 다른 종목을
추가할 수 있다. 원금·분할은 종목마다 따로 정하고, 추가해도 기존 종목 설정은 바뀌지 않는다.

두 종목은 같은 계좌의 달러를 함께 쓴다.
- 아침 요약·주문 1시간 전 알림의 입금 안내는 **두 종목 합계**로 비교한다
- 17:02 접수 때 달러가 한 종목분만 있으면, 먼저 접수하는 종목만 사고 나머지는 매수를
  건너뛴다 (실시간 주문은 접수 즉시 주문가능금액을 묶는다)

> 같은 계좌에 **개인 보유분**이 있는 종목은 주의. 봇은 증권사 잔고와 장부를 대조하므로,
> 개인 물량이 있으면 "장부 불일치"로 정지하고 자동 교정이 개인 물량을 봇 장부로 가져간다.
> 봇으로 운용할 종목은 개인 보유분을 정리한 뒤 시작한다.

### 앱에서 직접 취소한 뒤 다시 내기

키움 앱에서 봇의 LOC 주문을 취소한 뒤 `/run loc`을 치면 다시 접수된다. 접수 직전에
증권사 미체결과 원장을 대조해, 미체결에서 사라진 LOC를 취소로 반영하기 때문이다.
LOC는 종가 전에는 체결될 수 없으니 사라졌다면 취소가 확실하다.

지정가는 장중에 체결됐을 수도 있어 자동 반영하지 않는다. 미체결 조회가 실패하면
아무것도 바꾸지 않는다(확인 없이 반영하면 살아 있는 주문을 한 번 더 내게 된다).

### 매일 부족분을 채우는 운용

원금은 장부상 금액(예: $20,000)으로 두고, 실제 달러는 매일 그날 주문에 필요한 만큼만
채워 넣을 수 있다. 무한매수법 계산(1회매수액 = 잔금 ÷ 남은 분할)은 장부 기준으로
돌고, 증권사 계좌에는 그날 주문을 받을 만큼만 있으면 된다.

이 방식에서 달러 부족은 장부 이상이 아니라 "아직 입금 전"이라 다음처럼 처리한다.

| 상황 | 동작 |
|---|---|
| 08:00 아침 요약 | 오늘 필요 금액 / 현재 가능 금액 / **입금 필요액** 표시 |
| 주문 1시간 전 (16:00) | 모자라면 한 번 더 알림 |
| 주문 접수 (17:15) | 모자라면 **매수만 건너뛰고 매도는 접수** |
| 입금 후 | `/run loc` — 이미 낸 매도는 빼고 매수만 다시 접수 |

회로차단기는 걸지 않는다. 걸면 입금해도 풀리지 않아 그날 주문이 통째로 빠지고
매도까지 막힌다.

매수 가능 금액은 `ust31490`의 **미수불가 주문가능금액**(`min_ord_alowa`)을 쓴다.
증거금 기준 금액에는 미수가 섞여 있어, 그걸 믿고 사면 결제일에 미수가 생기고
반대매매로 이어질 수 있다.

### 아침 요약

EOD 리포트는 05:30에 오는데 대개 자고 있어 읽히지 않는다. 08시에 어제 결과와
오늘 예정을 한 번 더 보낸다.

`/fix`를 인자 없이 치면 버튼으로 진행한다. 적용 전 전후 비교를 보여주고 확인을 받는다.

**정지 후 복구 순서가 중요하다.** 회로차단기는 정지하면서 이미 수량·평단을 증권사
기준으로 교정한다. 그래서 정지 직후에는 수량 차이가 0이고, 거기서 수량을 또 보정하면
오히려 어긋난다. 남는 문제는 **T값**이다 — 어떤 체결을 놓쳤는지 모르니 T만 틀어진 채
남는다. `/fix`가 차이 여부를 보고 T 조정을 먼저 제시하는 이유다.

```
장부 60주 = 증권사 60주 — 수량은 이미 맞습니다.
남은 문제는 T값일 가능성이 높습니다.

[ T값 조정 ]
[ 매수 추가 ]  [ 매도 추가 ]
```

T 조정은 잔고 역산값(`보유원가 ÷ (원금÷분할수)`)을 후보로 제시하고, 바뀐 뒤
1회매수액과 별지점이 어떻게 달라지는지 미리 보여준다.

### 손익 표시가 두 가지인 이유

리포트에 실현손익이 두 가지로 나온다.

| 표시 | 계산 |
|---|---|
| 실현손익 (이동평균 기준) | (매도가 − 이동평균 평단) × 수량 |
| 사이클 누적손익 | 사이클 종료 시 잔금 − 시작 잔금 |

둘은 다르다. 151달러 물량이 있는 상태에서 120달러에 추매하면 평단이 143.5달러가
되고, 130달러에 팔면 증권사 계좌에는 **실현손실**로 찍히지만 그 물량 자체는 이익이다.
현금이 실제로 얼마나 늘었는지가 진짜 성적이므로 둘을 함께 보여준다.

> `/pause`는 **신규 주문 접수만** 멈춘다. 이미 증권사에 접수된 예약주문은
> 그대로 살아 있으므로, 취소가 필요하면 증권사 앱에서 직접 처리해야 한다.

스케줄러·EOD 결과는 자동으로 관리자에게 전송된다. 특히 아래는 반드시 확인한다.

- **예약주문 거부** — 증거금 부족, 가격제한폭 초과 등
- **체결 매칭 실패** — 원장에 없는 체결(수동 주문 등)
- **이상 조합** — 종가 판정상 불가능한 체결 조합이 관측됨

## 알려진 미확인 사항

실행으로 검증되지 않은 부분이다. 운영 전에 확인할 것.

0. **통합 시나리오** — 모듈별로는 검증했지만 접수→체결→정산→다음날 계획이
   실제로 한 바퀴 돈 적이 없다
1. **SOXL의 `stex_tp`** — `NA`로 두었으나 추측이다. `resolve_exchange()`로 확정할 것
2. **예약주문 접수 응답 구조** — `rsrv_ord_no` 필드명이 실제와 맞는지
3. **시세 부호 처리** — `"-198.4500"`을 하락 표시로 보고 절댓값을 취한다
4. **모의투자의 LOC/MOC 지원 여부**
5. **SEC/TAF 요율** — `config/fees.py`의 기본값은 대략치다. 증권사 고지 기준으로 갱신할 것
6. **리버스 소진 후 MOC 매도 수량** — 1단계와 동일하게 10/20등분(내림)으로 두었다.
   40분할 기준 보유 19주 이하가 되면 20등분이 0주가 되어 매도가 멈춘다.
   잔여 물량 처리 규칙이 방법론에 없어 경고만 남기고 사람이 판단하도록 했다

### 방법론 문서의 오타로 보이는 곳

리버스 쿼터매수 예제(3-(3))에서 1회 매수금액 544.47, 별지점 48.61일 때
폭락대비가 `45.37 / 41.88 / 38.83 / 36.29`로 적혀 있는데 세 번째가 맞지 않는다.

```
544.47/12 = 45.3725 → 45.37  일치
544.47/13 = 41.8823 → 41.88  일치
544.47/14 = 38.8907 → 38.89  문서는 38.83
544.47/15 = 36.2980 → 36.29  일치
```

네 번째가 `/15`와 정확히 맞으므로 세 번째도 `/14`가 맞다고 보고 계산값을 쓴다.

### 회로차단기

매일 EOD 후 전략 장부와 증권사 실제 잔고를 대조한다. 어긋나면 **신규 주문을 멈춘다.**

| 상황 | 조치 |
|---|---|
| 보유수량 불일치 | 정지 |
| 평단 괴리 5% 이상 | 정지 |
| 예수금 부족 | 정지 |
| EOD 2회 연속 실패 | 정지 |
| 평단 차이 1~5% | 알림만 (증권사 값으로 교정) |
| 이력 합계 ≠ 장부 수량 | 알림 (체결 누락 의심) |
| 잔고 조회 실패 | 알림만 |

**장부는 항상 증권사 기준으로 자동 교정된다.** 증권사 잔고가 사실이고 전략 장부는
추정이므로, 어긋나면 보유수량과 평단을 맞춘다. 교정 내역은
`data/archive/corrections_<종목>.jsonl` 에 남는다(비파괴).

다만 **T값은 교정하지 않는다.** T는 체결의 순서와 종류로 결정되므로 잔고만으로는
복원할 수 없다. 그래서 차이가 2주(또는 3%)를 넘으면 장부를 맞추면서 **동시에 정지**한다.
장부만 맞추고 계속 매매하면 T가 틀린 채로 주문이 나가기 때문이다.

> 첫 사이클에서는 우리 계산 평단과 키움 값이 매일 얼마나 벌어지는지 지켜볼 것.
> 증권사마다 매도 시 원가 산정 방식(이동평균 / FIFO / 매도대금 차감)이 달라
> 구조적 차이가 날 수 있다. 실측으로 확인되면 그때 기준을 조정한다.

교차검증으로 잔고에서 T를 역산해 비교한다.

```
T ≈ (보유수량 × 평단) / (원금 / 분할수)
```

원가 기준으로 보면 방법론 규칙과 맞물린다 — 쿼터매도는 원가 ×0.75, 3/4 지정가매도는
×0.25, 리버스 10등분 매도는 ×0.9. 폭락대비 매수(T 불변)와 1회매수금 변동 때문에
정확히 같지는 않으므로, 대체값이 아니라 경고용으로만 쓴다.

정지는 **자동으로 풀리지 않는다.** 다음 대조가 정상으로 나와도 유지된다.
원인이 남은 채 다시 주문이 나가는 것을 막기 위해서다. 증권사 앱에서 실제
잔고를 확인하고, 필요하면 `/fix`로 보정한 뒤 `/unhalt <종목>`으로 푼다.

정지 상태는 상태 파일에 저장되므로 프로세스를 재시작해도 유지된다.

> `/halt`와 `/pause`는 다르다. `/halt`는 종목별 주문 정지(상태에 기록, 재시작 후에도 유지),
> `/pause`는 스케줄러 전체 일시정지(메모리상, 재시작하면 풀림)다.
> 둘 다 **이미 접수된 주문은 취소하지 않는다.**
